Deploy on Friday Product Vision

Terminal-native incident-management satire, main deck, extension packs, mixed themes, and the first product roadmap.

Product Promise

Deploy on Friday is a terminal-native multiplayer incident-management satire where software engineers survive the history, culture, hype cycles, failures, and rituals of the software industry. The core game should be easy to learn, deterministic enough to test, and expandable through thematic content packs.

The player fantasy is simple: assemble an engineering identity, survive absurd technical and organizational disasters, negotiate with other players, sabotage at the right time, and become the first Principal Engineer.

Market Positioning

Market research points to a focused niche with strong community potential and medium commercial upside. The product should not try to look like a generic tabletop card-game clone. Its ownable position is developer identity plus terminal-native multiplayer chaos.

Core Product Model

The game has one evergreen main deck and many optional extensions.

The main deck represents general software engineering: bugs, technical debt, production incidents, tools, career progression, code review, architecture, testing, deployment, security, and team dynamics.

Extensions represent emblematic eras or subcultures. They add cards, card classes, achievements, optional mechanics, and themed deck recipes without replacing the core rules. The commercial model is paid ownership plus in-game unlock progression: buying or otherwise owning a pack grants access to that theme, while gameplay progression unlocks recipes, achievements, cosmetic profile items, or advanced variants inside the owned content.

Players should be able to:

  • Play with only the main deck.
  • Unlock one extension and add it to the match.
  • Combine multiple extensions in the same match.
  • Mix compatible card classes from different extensions.
  • Use official deck recipes or custom deck selection rules.

Multi-Mentor Product Meeting Summary

Product Owner decision: the main deck remains broad software-engineering satire. The extension system becomes the long-term content and progression axis. Unlocking extensions and choosing deck mixes are first-class product capabilities, not late polish.

Game engineer guidance: keep the core loop stable. Extensions should initially add cards, deck recipes, achievements, and limited keyword mechanics. Avoid extension-specific rule engines until at least two extensions prove the same mechanic shape is needed.

Architecture lead guidance: model extensions as content catalogs and match configuration inputs. The domain should know about card definitions, deck membership, compatibility tags, card classes, unlock status, and match deck recipes. Infrastructure loads these facts, but PostgreSQL must not define the domain language.

Technical naming guidance: the public product title must not become the implementation namespace. Use stable generic identifiers such as game_ for C symbols, CMake targets, database examples, protocol examples, and test binaries.

Commercial Strategy

The recommended business model is low-cost premium plus optional content, not aggressive free-to-play.

  • Public demo: default deck, local play with bots, 3 completed online matches per account per day, one-command startup, abandoned-match cooldown protection, and replay logs.
  • Demo quota policy: only completed online matches consume the daily quota; repeated abandoned or disconnected matches trigger a temporary cooldown instead of spending quota.
  • Paid gate: do not charge for early access until official online multiplayer exists. The social loop is the strongest retention hook and must be real before asking for money.
  • Early access: full main deck, official online multiplayer, rankings, deterministic match transcripts, and low trial-friendly price.
  • v1.0: polished main game with official servers and stable deck recipes.
  • Extensions: small paid content packs with cards, achievements, deck recipes, terminal themes, and at most one lightweight mechanic. Ownership grants theme access; in-game progression unlocks recipes, cosmetics, achievements, and advanced variants without selling stronger cards directly.
  • Supporter pack: cosmetic badges, title screen variants, profile titles, soundtrack or terminal ambience, and no gameplay advantage.
  • Avoid: loot boxes, pay-to-win card packs, and battle passes before the audience is large enough to justify constant content production.

Basic Roadmap

v0.1 Root Prototype

Goal: prove the deterministic local turn loop with seeded main-deck content and Incident Severity as the first signature mechanic.

Scope: main deck only, Encounter and Treasure deck construction from seed data, deterministic RNG, local simulation, terminal smoke path, content validation before match startup, and a visible Incident Severity meter that players can reduce, ignore, exploit, or escalate.

Out of scope: unlocks, extension mixing, persistent accounts, and real multiplayer.

v0.2 Modular Content Foundation

Goal: introduce extension-aware content metadata without changing the player loop, while preserving the main deck as a standalone demo candidate.

  • Extension metadata model.
  • Card-to-extension mapping.
  • Card class and compatibility tags.
  • Deck recipe validation.
  • Main deck as the default recipe.
  • Test fixtures for one small sample extension.

v0.3 Unlocks And Custom Deck Selection

Goal: let players select unlocked extensions for a match and prepare the first public demo/playtest funnel.

  • Player extension unlock state.
  • Match configuration that lists selected extensions.
  • Server-side validation of selected content.
  • Basic terminal flow for selecting available extensions.
  • Persistence for unlocks and match deck configuration.
  • Copy-paste invite command, bot fallback, and 3 completed online matches per account per day for low-friction public demo testing.

v0.4 Mixed Theme Alpha

Goal: support multiple selected extensions in one match.

  • Mixed deck recipe construction.
  • Compatibility checks.
  • Balance bands for mixed Encounter and Treasure pools.
  • First public-style playtest with at least two extensions enabled.

v1.0 Core Game

Goal: ship the complete main-deck experience with the extension framework ready.

  • Stable server-authoritative multiplayer loop.
  • Main deck balance pass.
  • Extension-compatible content catalog.
  • Achievements.
  • Rankings and match history.
  • Deck recipe validation gates.

v1.x Extension Releases

Goal: ship themed extensions incrementally without destabilizing the core game.

Initial sequence: The Punch Card Era, The .com Bubble, I'm a Developer, The SaaS Bubble, and The AI New Era.

Each extension should ship with a theme promise, card list, deck recipe impact, achievements, balance notes, compatibility tags, validation tests, and a release gate proving the main deck still works alone.

Product Risks

  • Scope creep: extensions can easily become new games. Keep first versions content-heavy and mechanic-light.
  • Balance complexity: mixed decks can create extreme combinations. Use power bands, rarity, compatibility tags, and playtest transcripts.
  • Implementation coupling: avoid hardcoding extension behavior in the UI, database layer, or server packet names. Extension data should flow into stable domain/application APIs.
  • Player confusion: deck construction must be explainable. Start with official recipes before offering fully custom deck builders.
  • IP and positioning risk: public docs, store pages, card layout, and terminology must avoid brand comparisons or clone-like expression.
  • Terminal friction: the unique UI is a strength only if install, setup, match start, and command readability are excellent.
