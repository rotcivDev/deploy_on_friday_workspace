Deploy on Friday Workspace

Deploy on Friday is a terminal-native multiplayer incident-management satire where developers weaponize bugs, tools, influence, tech debt, and production chaos to become Principal Engineer.

This repository is organized as a mentorship-first C17 project. The production source tree is intentionally protected from agent edits so the human developer keeps hands-on ownership of the implementation.

Product Direction

The product is built around a modular deck model and a deliberately developer-native identity:

  • The main deck carries the evergreen software-engineering theme.
  • Emblematic eras and subcultures ship as extensions.
  • Players unlock extensions and choose which decks participate in a match.
  • Extensions can be mixed, allowing card classes and themes from different eras to interact in the same game.

Planned extension examples include:

  • The Punch Card Era
  • The .com Bubble
  • I'm a Developer
  • The SaaS Bubble
  • The AI New Era

See PRODUCT.html for the full product vision and roadmap.

Market Position

The strongest audience is not the mass-market card-game audience. It is developers who want a funny, low-friction game to play with developer friends. The product should lean into terminal-native identity, short bot-supported matches, replayable logs, and shareable screenshots.

  • Public positioning: incident-response multiplayer satire with terminal-native identity. Workplace satire is the tone; software-history eras are expansion flavor.
  • Avoid public comparison to existing tabletop brands or clone-like wording.
  • First playable promise: free demo with the default deck, one-command local match with bots, 3 completed online matches per account per day, abandoned-match cooldown protection, and a readable terminal UI.
  • v0.1 signature mechanic: Incident Severity, a shared production-chaos pressure meter that players can reduce, ignore, exploit, or escalate.
  • Commercial shape: free demo first; no paid build until official online multiplayer exists; then low-cost base game, extension ownership plus in-game unlock progression, optional supporter cosmetics, and no pay-to-win cards.

Technical Project

The technical project targets a deterministic, server-authoritative terminal game:

  • Language: C17
  • Build: CMake with Make workflow wrappers
  • UI: NCurses terminal client
  • Runtime: POSIX sockets and pthreads
  • Persistence: PostgreSQL
  • Tests: CTest
  • Architecture: domain-first Clean Architecture

The implementation should treat cards, decks, card classes, extensions, unlock rules, match configuration, and content validation as domain concepts first. PostgreSQL tables, repositories, CMake targets, protocol packets, and terminal screens are tactical tools that serve those concepts.

Technical identifiers must not depend on the public product title. Use stable generic names such as game_ in C symbols, build targets, database examples, and protocol examples so the public title can change without forcing a codebase rename.

TDD and observability are non-negotiable. Every accepted behavior needs a prior failing check and structured evidence that explains actor/session, command path, correlation id, replay seed, state transition, result, and failure mode. See TDD and observability policy.

Agent Boundary
