Deploy on Friday Modular Deck Strategy

Product Owner, game engineer, and architecture lead alignment for the extension-based product vision.

Decision

Deploy on Friday should ship with a broad main deck for general software-engineering satire, then grow through optional extensions. Players unlock extensions, select which content packs participate in a match, and can mix compatible card classes from different themes.

Product rule: extensions expand the card catalog and deck recipes; they must not fork the core game loop.

Core Concepts

  • Main Deck: required evergreen cards for the basic software-engineering experience.
  • Extension: a named content pack with metadata, cards, classes, deck recipes, achievements, and compatibility tags.
  • Deck Recipe: rules that construct match draw piles from selected content packs.
  • Card Class: reusable gameplay grouping such as Monster, Equipment, Curse, Event, PvP, AI-Chaos, Legacy, Infrastructure, Business, Career, or Community.
  • Compatibility Tag: a validation and balancing marker such as core, retro, startup, saas, ai, or high-chaos.
  • Unlock: player/account permission to select an extension for a match.

Architecture Shape

The implementation should preserve the existing dependency direction:

  • Domain: validates card definitions, card classes, deck recipes, selected extensions, compatibility tags, deterministic deck construction, and match rules.
  • Application: coordinates match setup, selected extensions, unlock checks, content validation, and command results.
  • Infrastructure: loads extension metadata, cards, deck membership, unlock state, and achievements from PostgreSQL.
  • Server: validates client match setup requests and owns the authoritative selected deck recipe.
  • Client: shows available extensions and selected recipe summaries; it does not validate ownership or balance.

Development Consistency Rules

  • Every extension must pass the same content validation path as the main deck.
  • Every mixed deck must be reproducible from selected extension IDs, recipe IDs, and RNG seed.
  • Extension cards should use existing card classes before introducing new ones.
  • New mechanics must include deterministic tests and a fallback rule when mixed with unrelated extensions.
  • The main deck must remain playable alone after every extension patch.

First Implementation Slice

  1. Add extension metadata to support docs and seed templates.
  2. Represent the main deck as a content pack named main-software-engineering.
  3. Add a deck recipe concept to validation plans.
  4. Build one tiny sample extension fixture with 6 to 10 cards.
  5. Prove one deterministic match can load main deck only and another can load main deck plus the sample extension.
