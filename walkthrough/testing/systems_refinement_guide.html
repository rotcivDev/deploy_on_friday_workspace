Systems Backlog Refinement Guide: v0.1 Prototype

This document evaluates the systems programming impact of walkthrough/architecture/kickoff_backlog.html and refines the build, test, memory, deterministic runtime, and terminal-client work into increments for the v0.1 Root Prototype.

This is a mentorship and support artifact. It does not require agents to edit production source directories.

1. Backlog Review Summary

Second Review: Source-of-Truth Alignment. Systems work should make the domain feedback loop fast and trustworthy. C17 APIs, ownership rules, CMake targets, CTest suites, deterministic RNG, and Docker wrappers are valuable only when they preserve domain boundaries and expose reproducible evidence. Avoid building generic systems infrastructure before a domain use case needs it.

The kickoff backlog correctly shifts the v0.1 prototype toward a local, deterministic, Clean Architecture shape. From a systems perspective, the main risk is not sockets or pthreads yet; those are explicitly deferred. The main risk is accidentally building the prototype as one tangled executable where forbidden dependencies are impossible to detect.

The systems plan needs four refinements before implementation starts:

  • Build targets must enforce the architecture boundary from A1 instead of compiling every source file into one executable.
  • Tests must cover deterministic shuffling, command results, lifecycle cleanup, and snapshot rendering without requiring NCurses or PostgreSQL for every test.
  • Memory ownership needs a header-level contract before dynamic decks, hands, snapshots, and repository result arrays spread through the code.
  • Networking and threaded server work should stay deferred for v0.1, but the command boundary should be shaped so it can become the v0.2 protocol boundary.

2. v0.1 Systems Scope

In Scope

  • C17 build scaffolding with -std=c17 -Wall -Wextra -Werror -pedantic.
  • CMake targets wrapped by make commands.
  • Layered build targets for domain, application, infrastructure database adapter, NCurses client, and tests.
  • CTest suites for domain rules, deck determinism, command boundaries, repository fakes, and lifecycle cleanup.
  • Explicit deterministic RNG guidance for shuffles and bot decisions.
  • Memory ownership rules for public interfaces.
  • NCurses layout guidance that renders application snapshots and sends commands.

Out Of Scope For v0.1

  • POSIX socket server/client networking.
  • pthread worker pools, connection pools, or lobby concurrency.
  • Binary network packet structs.
  • Shared protocol serialization.
  • Reconnect, spectator mode, and remote synchronization.
  • Runtime persistence of match events unless explicitly chosen as a spike.

3. Backlog Alignment Findings

Finding 1: A1 Needs Target-Level Dependency Enforcement

The earlier systems guide used a single dungeon_client executable that directly included domain, application, infrastructure, and client sources together. That compiles, but it does not prove the architecture. A1 needs separate libraries so dependency mistakes fail during build review and test setup.

Recommended target shape:


game_domain
    C standard library only

game_application
    links game_domain

game_infrastructure_db
    links game_application + game_domain + libpq

game_client_ncurses
    links game_application + game_domain + game_infrastructure_db + ncurses

game_tests_domain
    links game_domain

game_tests_application
    links game_application + game_domain + fake repositories

Design rule:

  • Domain tests must run without PostgreSQL, NCurses, sockets, or filesystem fixtures.
  • Application tests should use fake repositories unless the test is specifically an infrastructure adapter test.
  • Infrastructure database tests can require local PostgreSQL, but they should be tagged or separated so normal make test can remain fast.

Finding 2: R2, R3, And A6 Need A Deterministic RNG Contract

The backlog requires deterministic deck order and bot choices. C rand() is not suitable because behavior can differ by platform and hidden global state makes replay difficult.

Recommended contract:


rng_state(seed)
rng_next_u32(state)
rng_range(state, upper_bound)
deck_shuffle(deck, rng_state)
bot_choose_action(bot, snapshot, rng_state)

Guidance:

  • Store RNG state in match/application state.
  • Pass the RNG state explicitly to shuffle and bot decisions.
  • Never call rand() inside domain rule functions.
  • Record the seed in the match log so a failed simulation can be replayed.

Finding 3: R4, R5, And A7 Need Structured Result Tests

Combat, curse, and bot actions should return typed outcomes and event records. If the UI has to infer what happened from mutated state, tests and logs will become brittle.

Recommended command result shape:


status_code
updated_snapshot
event_count
events[]
error_code

Test target:

  • Valid command changes state and emits ordered events.
  • Invalid command leaves state unchanged.
  • Combat win emits reward events before match-ended events.
  • Curse resolution emits a visible event and clears or sets explicit temporary state.

Finding 4: A8 Needs Ownership Rules Before Dynamic Containers Grow

Decks, hands, discard piles, snapshots, and repository-loaded arrays create several ownership edges. The prototype should document them before implementation.

Recommended C ownership vocabulary:

Pattern Meaning
create / destroy Function allocates and caller must eventually destroy
init / deinit Caller owns storage, function initializes contents
borrow Pointer valid until the next mutation or destroy
copy Caller receives independent value or allocated data
free_result Matching cleanup for adapter-returned arrays

Header comments should state whether a returned pointer is owned, borrowed, or copied.

Finding 5: R7 Needs A Non-Interactive UI Smoke Path

NCurses is hard to test in full automation, but R7 asks for at least one non-interactive render smoke test if feasible.

Recommended approach:

  • Keep the UI rendering function snapshot-driven.
  • Provide a static snapshot fixture for tests.
  • Split layout calculation from actual WINDOW drawing where practical.
  • Test the layout calculator without NCurses.
  • Keep interactive resize checks as manual playtest items.

4. Increment Plan

SP0. Layered Build Skeleton

Outcome: establish build targets that match A1 before real gameplay code grows.

Scope:

  • Define separate CMake library targets for domain, application, infrastructure DB, and client.
  • Add a Makefile wrapper for make configure, make build, make test, and make clean.
  • Keep PostgreSQL and NCurses linked only by the targets that need them.
  • Add a minimal CTest smoke target.

Acceptance criteria:

  • Domain target compiles without libpq, NCurses, pthreads, or socket libraries.
  • Application target depends on domain and application ports only.
  • Infrastructure DB target is the only target that links libpq.
  • Client target is the only target that links NCurses.

Verification:

  • make build
  • make test
  • Manual target dependency review.

SP1. Deterministic RNG And Deck Test Harness

Outcome: make R2, R3, and A6 testable on every run.

Scope:

  • Define a small seedable RNG API for deterministic tests.
  • Document Fisher-Yates shuffle as the expected deck shuffle algorithm.
  • Add tests for repeated shuffle order with the same seed.
  • Add tests for discard reshuffle behavior.

Acceptance criteria:

  • Same seed produces the same Encounter and Treasure draw order.
  • Different seeds can produce different orders.
  • Empty deck reshuffle consumes RNG state deterministically.

Verification:

  • CTest domain deck tests.
  • Fixed-seed transcript captured in test output on failure.

SP2. Domain Rule And State Tests

Outcome: prove R4 and R5 without PostgreSQL or NCurses.

Scope:

  • Test Level bounds.
  • Test Power calculation.
  • Test combat win/loss.
  • Test fallback bad stuff.
  • Test seeded curse state transitions.

Acceptance criteria:

  • Level never drops below 1 or exceeds 10.
  • Power formula matches Level + class base_power_bonus + equipment power_bonus + temporary modifiers.
  • Broken CI, Scope Creep, and Context Window Exceeded each have deterministic tests.

Verification:

  • game_tests_domain
  • Optional leak-check run where available.

SP3. Application Command Boundary Tests

Outcome: prove A4 and A7 before the NCurses client depends on them.

Scope:

  • Create fake content repositories for match startup tests.
  • Test command success and invalid-phase failures.
  • Test event ordering for card draw, combat, curse, bot action, and match end.
  • Test bot commands through the same validation path as human commands.

Acceptance criteria:

  • Invalid commands return typed errors and leave state unchanged.
  • Successful commands return updated snapshots and ordered events.
  • Bot decisions are deterministic for a fixed seed.

Verification:

  • game_tests_application
  • Full-match simulation test with one fixed seed.

SP4. Repository Adapter Mapping Tests

Outcome: prove Epic 2 row mapping without letting PostgreSQL types escape into application/domain code.

Scope:

  • Test row-to-content mapping against the walkthrough seed data.
  • Keep PGconn and PGresult private to infrastructure.
  • Add cleanup tests for repository result arrays.
  • Separate these tests from pure domain/application tests.

Acceptance criteria:

  • Adapter returns plain content structs.
  • Missing DB content returns a typed startup failure.
  • Result arrays have matching cleanup functions.

Verification:

  • Local PostgreSQL adapter test, run explicitly when the database is available.
  • Fake repository tests remain available for normal make test.

SP5. Snapshot-Driven NCurses Smoke Path

Outcome: make R7 testable enough without automating a whole terminal session.

Scope:

  • Document snapshot fields required by the UI.
  • Split layout calculation from drawing where practical.
  • Add a non-interactive static snapshot render or layout smoke test.
  • Add a manual resize checklist.

Acceptance criteria:

  • UI renders application snapshots only.
  • UI sends commands and does not mutate match state directly.
  • Static snapshot smoke test proves the expected panels can be produced.

Verification:

  • Non-interactive layout test where feasible.
  • Manual terminal playtest checklist.

SP6. Deferred v0.2 Protocol Preparation

Outcome: keep v0.1 local while preserving a clean path to future networking.

Scope:

  • Treat application commands as the future network protocol shape.
  • Avoid putting NCurses-only concepts in command/result structs.
  • Do not introduce socket headers or binary packet layouts in v0.1 production code.
  • Keep protocol notes in walkthrough documentation only.

Acceptance criteria:

  • Command names and result payloads are stable enough to map to v0.2 opcodes later.
  • No v0.1 target requires POSIX sockets.
  • No shared binary protocol files are required for local play.

Verification:

  • Header review checklist.
  • Build target dependency review.

5. CMake Target Template

Use this as a design guide for the user-created root CMakeLists.txt. File names are illustrative and should be adapted to the actual implementation.


cmake_minimum_required(VERSION 3.16)
project(GameCore C)

set(CMAKE_C_STANDARD 17)
set(CMAKE_C_STANDARD_REQUIRED ON)
set(CMAKE_C_EXTENSIONS OFF)

add_compile_options(-Wall -Wextra -Werror -pedantic)

enable_testing()

add_library(game_domain
    domain/card.c
    domain/deck.c
    domain/player.c
    domain/game_rules.c
)
target_include_directories(game_domain PUBLIC domain)

add_library(game_application
    application/game_service.c
    application/bot_ai.c
)
target_include_directories(game_application PUBLIC application)
target_link_libraries(game_application PUBLIC game_domain)

find_package(PostgreSQL REQUIRED)
add_library(game_infrastructure_db
    infrastructure/db/postgresql_content_repository.c
)
target_include_directories(game_infrastructure_db PRIVATE ${PostgreSQL_INCLUDE_DIRS})
target_link_libraries(game_infrastructure_db PRIVATE game_application game_domain ${PostgreSQL_LIBRARIES})

find_package(Curses REQUIRED)
add_executable(game_client_ncurses
    client/ncurses_ui.c
    client/main.c
)
target_include_directories(game_client_ncurses PRIVATE ${CURSES_INCLUDE_DIR})
target_link_libraries(game_client_ncurses PRIVATE game_application game_domain game_infrastructure_db ${CURSES_LIBRARIES})

add_executable(game_tests_domain
    tests/domain/test_deck.c
    tests/domain/test_combat.c
)
target_link_libraries(game_tests_domain PRIVATE game_domain)
add_test(NAME domain COMMAND game_tests_domain)

add_executable(game_tests_application
    tests/application/test_commands.c
    tests/fakes/fake_content_repository.c
)
target_link_libraries(game_tests_application PRIVATE game_application game_domain)
add_test(NAME application COMMAND game_tests_application)

Important boundary check:

  • Do not link game_tests_domain to PostgreSQL or NCurses.
  • Do not include libpq-fe.h outside infrastructure DB files.
  • Do not include ncurses.h outside client UI files.

6. Makefile Wrapper Template

Use make as the day-to-day interface, while CMake owns target generation.


.PHONY: configure build test test-db run clean

BUILD_DIR := build

configure:
	cmake -S . -B $(BUILD_DIR)

build: configure
	cmake --build $(BUILD_DIR)

test: build
	ctest --test-dir $(BUILD_DIR) --output-on-failure

test-db: build
	ctest --test-dir $(BUILD_DIR) --output-on-failure -L db

run: build
	./$(BUILD_DIR)/game_client_ncurses

clean:
	cmake -E rm -rf $(BUILD_DIR)

Dependency installation should stay outside the default build path. If a setup target is added, make it explicit and document that it may require system package manager privileges.

8. Memory Ownership Checklist

Use this checklist during header review:


Does every create/init function have a matching destroy/deinit?
Does every adapter result array have one cleanup function?
Are borrowed pointers documented as invalid after mutation?
Are returned snapshots copied or clearly owned by the caller?
Can a failed initialization clean up all partial allocations?
Can tests create and destroy a full match without reachable allocations?

Recommended naming:


match_create / match_destroy
deck_init / deck_deinit
content_result_free
snapshot_destroy
command_result_deinit

Avoid returning pointers into resizable arrays unless the lifetime is deliberately short and documented.

10. v0.2 Networking Notes

Do not implement sockets in v0.1. Preserve the path by keeping commands and results serializable:


START_LOCAL_MATCH
KICK_BACKLOG
EQUIP_CARD
PLAY_CARD
REQUEST_HELP
RESOLVE_COMBAT
END_TURN
RESOLVE_BOT_TURN

When v0.2 starts, these commands can map to explicit opcodes with a fixed header:


+------------------+------------------+--------------------+--------------------+
| Magic Bytes (2B) | Opcode (2B)      | Payload Length(4B) | Payload            |
+------------------+------------------+--------------------+--------------------+

For now, keep that as documentation only. The v0.1 build should not depend on socket headers, shared packet structs, or pthread worker pools.
