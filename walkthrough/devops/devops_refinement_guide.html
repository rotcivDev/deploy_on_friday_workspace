DevOps Backlog Refinement Guide: v0.1 Prototype

This document evaluates the v0.1 backlog and the existing team refinement guides from the DevOps and infrastructure-readiness perspective. It turns the architecture, systems, database, and gameplay increments into a reproducible local build/test/run plan for the Dungeons and Devs Root Prototype.

This is a mentorship and support artifact. It does not require agents to edit production source directories.

1. Reviewed Inputs

This DevOps pass reviewed:

  • kickoff_backlog.html: R1-R7 playable prototype stories and A1-A8 architecture guardrails.
  • lead_architecture_refinement_guide.html: unified increment order AR0-AR8.
  • gameplay_refinement_guide.html: fixed-seed playtest, balance targets, bot rules, and terminal playtest notes.
  • db_refinement_guide.html: seed validation, deck membership, repository port, and deferred JSONB persistence.
  • systems_refinement_guide.html: layered CMake targets, Make wrapper, deterministic RNG, CTest matrix, memory checks, and NCurses smoke path.

2. DevOps Review Summary

Second Review: Source-of-Truth Alignment. DevOps serves the domain by making learning reproducible. Docker/Compose should now be the recommended first-time path for dependency isolation, but it remains a local feedback tool, not the v0.1 production architecture. Compose services, Make targets, CI gates, seed validation, and artifacts must protect domain tests, content validation, and fixed-seed simulations without collapsing architecture boundaries.

The team plans are aligned around a local-first prototype: a C17/CTest build, PostgreSQL-seeded content, deterministic in-memory match simulation, and an NCurses client that renders application snapshots.

The DevOps risk is operational drift: if setup, seed loading, test selection, and release checks stay informal, each increment can appear complete on one machine while failing on another. The v0.1 plan needs a documented local environment contract and a small CI-style gate sequence before runtime complexity grows.

DevOps recommendation:

  • Make make the single day-to-day interface for configure, build, unit tests, optional DB tests, run, and cleanup.
  • Keep normal tests independent of PostgreSQL and NCurses where the architecture requires it.
  • Treat database seed validation as a startup and test gate, not a manual afterthought.
  • Capture fixed seeds, simulation transcripts, logs, and failure output as debugging artifacts.
  • Keep v0.1 local-only. Do not introduce cloud deployment, Kubernetes, production networking, connection pools, or secrets platforms before the local deterministic loop is stable.

3. v0.1 DevOps Scope

In Scope

  • Local development prerequisites for C17, CMake, Make, CTest, PostgreSQL client/server or local service, libpq, NCurses, and optional leak-check tooling.
  • Make-driven workflow design for configure, build, test, database seed setup, DB adapter tests, fixed-seed simulation, NCurses run, and cleanup.
  • CI gate design that preserves Clean Architecture boundaries.
  • Local database lifecycle guidance for applying walkthrough SQL and validating required content.
  • .env.example guidance for local DSNs, seeds, terminal mode flags, and log paths.
  • Runtime topology documentation for the local binary, optional PostgreSQL service, test database, logs, and artifacts.
  • Release/readiness checklist for the v0.1 Root Prototype.

Out Of Scope For v0.1

  • Cloud deployment.
  • Kubernetes or production orchestration.
  • Container-only development as a required path.
  • Secrets managers beyond local environment variables and ignored .env files.
  • Production observability stacks.
  • PostgreSQL connection pooling.
  • TCP server/client runtime deployment.
  • JSONB event persistence as a required release gate.

4. Backlog Alignment Findings

Finding 1: A1 And SP0 Need A Reproducible Command Surface

The systems plan correctly recommends CMake targets wrapped by Make. DevOps should formalize the day-to-day commands so contributors do not need to remember raw CMake, CTest, or psql invocations.

Recommended command contract:


make configure
make build
make test
make test-db
make db-reset
make db-seed
make db-validate
make simulate
make run
make clean

Acceptance target:

  • make test runs fast domain/application tests without requiring PostgreSQL or NCurses interaction.
  • make test-db is explicit and may require local PostgreSQL configuration.
  • make simulate runs one fixed-seed non-interactive match transcript when AR7 exists.
  • No default command installs packages or mutates system services.

Finding 2: R1, DB0, DB1, And DB3 Need A Local DB Lifecycle

The database guide defines seed SQL and validation queries. DevOps should package that as a repeatable lifecycle: create or reset a local test database, apply SQL in order, validate content, and leave readable diagnostics.

Recommended local lifecycle:


db-reset:
    drop and recreate local development database

db-seed:
    apply 01_schema.sql
    apply 02_seed_core_data.sql
    apply 03_seed_cards.sql
    apply 04_seed_achievements.sql
    apply 05_seed_deck_cards.sql when created

db-validate:
    confirm required card types, classes, decks, deck_cards quantities, and minimum content counts

Acceptance target:

  • Missing seed content fails before match creation.
  • Deck membership validation is available once DB1 adds 05_seed_deck_cards.sql.
  • DB adapter tests are labeled separately from pure domain/application tests.

Finding 3: Deterministic Simulation Should Become A CI Artifact

Gameplay and systems both depend on fixed seeds. DevOps should treat seed values and simulation transcripts as first-class debugging artifacts.

Recommended artifact capture:


artifacts/
    test-output/
    simulations/
        seed-<seed>.log
    db/
        validation.log
    crashes/

Acceptance target:

  • Failed simulation output includes the seed.
  • A fixed seed produces the same major event sequence.
  • The transcript records match start, deck setup, bot choices, combat results, curse effects, level gains, and winner.

Finding 4: CI Must Enforce Architecture Boundaries, Not Collapse Them

It is convenient to build one all-in executable, but that would hide the architecture risks the lead architect and systems guide identified.

Recommended CI stages:


checkout
configure
build layered targets
run domain tests
run application tests with fake repositories
run optional DB adapter tests when PostgreSQL is available
run optional static/dependency boundary checks
collect logs and test artifacts
review v0.1 release checklist

Acceptance target:

  • Domain/application tests do not link libpq or NCurses.
  • DB adapter tests are opt-in or separately labeled.
  • UI smoke checks are isolated from core rule tests.
  • Pipeline convenience never moves SQL, terminal rendering, or socket code into the wrong layer.

Finding 5: Configuration Needs To Be Explicit Before Runtime Growth

The first local prototype still has configuration: database DSN, seed, log level, artifact path, optional terminal behavior, and feature spikes. If these are hidden in source, the future v0.2 runtime will inherit avoidable operational debt.

Recommended .env.example values:


DTD_DB_DSN=postgresql://localhost/dungeons_devs
DTD_MATCH_SEED=12345
DTD_LOG_LEVEL=info
DTD_ARTIFACT_DIR=artifacts
DTD_ENABLE_DB_TESTS=0
DTD_ENABLE_EVENT_PERSISTENCE=0

Acceptance target:

  • Real credentials are never committed.
  • Local .env is ignored by Git.
  • Event persistence stays disabled by default for v0.1 unless explicitly chosen as a spike.

Finding 6: v0.1 Readiness Is Build/Test/Seed/Playtest, Not Deployment

The backlog defers server networking, persistence, accounts, rankings, and production deployment. The release gate should therefore measure reproducibility and playability, not cloud maturity.

Minimum release gate:


make clean
make build
make test
make db-reset
make db-seed
make db-validate
make test-db
make simulate DTD_MATCH_SEED=<known seed>
manual NCurses playtest checklist
architecture boundary checklist

Acceptance target:

  • A new contributor can reproduce the prototype from docs and local prerequisites.
  • The seed DB produces a non-empty Encounter deck and Treasure deck.
  • A fixed-seed simulation completes.
  • Manual terminal playtest captures seed, winner, turn count, confusing logs, and resize behavior.

5. DevOps Increment Plan

DEV0. Local Environment Contract

Outcome: define the host prerequisites and local setup expectations before implementation starts.

Consumes:

  • Architecture AR0.
  • Systems SP0.
  • Database DB0.

Scope:

  • Document required toolchain packages: C17 compiler, CMake, Make, CTest, PostgreSQL, libpq, NCurses, and optional Valgrind or sanitizer support.
  • Distinguish build-time dependencies from runtime services.
  • Keep package installation manual and platform-specific in docs; do not hide privileged installs behind default Make targets.

Acceptance criteria:

  • The team can name every local prerequisite for v0.1.
  • The normal build path does not require network access or package installation.
  • PostgreSQL is documented as a local service for DB tests and seeded startup, not a dependency of pure domain/application tests.

Verification:

  • Local environment checklist review.
  • First-run setup walkthrough.

Boundary notes:

  • Domain/application tests should not require PG.
  • GAME may load seeded content from PG at startup, then run the match in memory.
  • ART is local text output for v0.1: CTest output, DB validation logs, simulation transcripts, and manual playtest notes.
  • Future TCP server/client processes are not part of this topology.

8. Suggested CI Gate Template

Use this as a design target for future CI configuration. Keep it as documentation until the Git Specialist or DevOps task explicitly creates CI files.


stage: configure
    make configure

stage: build
    make build

stage: unit-tests
    make test

stage: db-tests
    make db-seed
    make db-validate
    make test-db
    condition: local/CI PostgreSQL service is available

stage: simulation
    make simulate DTD_MATCH_SEED=12345
    condition: AR7 simulation entry point exists

stage: artifacts
    collect build/Testing/Temporary/LastTest.log
    collect artifacts/db/validation.log
    collect artifacts/simulations/seed-12345.log

Do not make DB tests block early domain/application work until the adapter and local PostgreSQL setup exist. Once AR2/DB3 are implemented, DB validation should become a required gate for playable-release candidates.

10. v0.1 Release Checklist

Use this checklist for the first playable prototype candidate:


Clean build:
    make clean
    make build

Fast tests:
    make test

Database:
    make db-reset
    make db-seed
    make db-validate
    make test-db

Simulation:
    make simulate DTD_MATCH_SEED=12345
    transcript saved with seed, winner, turn count, and final event

Manual terminal playtest:
    seed recorded
    stats panel checked
    battle panel checked
    hand selection indexes stable
    bot actions visible in log
    curse/combat/equipment events visible
    terminal resize checked
    exit restores terminal state

Architecture boundary:
    domain has no libpq/ncurses/socket/pthread dependency
    application has no SQL or terminal rendering
    infrastructure keeps libpq private
    client renders snapshots and sends commands only
    DB tests are separated from pure tests

Deferred scope:
    no TCP server required
    no pthread worker pool required
    no account/ranking/achievement runtime required
    no JSONB event persistence required
    no cloud deployment required

This is the DevOps definition of ready for v0.1: reproducible local setup, deterministic test evidence, validated seed content, and a playable terminal loop.
