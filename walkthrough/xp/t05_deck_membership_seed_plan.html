T05 Implementation Plan: Add Deck Membership Seed Plan

Intent

Goal: Create a database seed containing deck names and map specific cards to the Encounter and Treasure decks with a valid quantity. Implement SQL check queries to validate deck structure.

A deck in Dungeon of Technical Debt is not just an array of items; it is a configured database relation where cards belong to specific decks with varying quantities (e.g. 3 copies of "Broken CI" in the Encounter deck, but 0 in the Treasure deck). We must establish this structure in SQL seeds and validate it before match load.

Implementation Story

Source backlog item: T05, R2, R3, DB1, GD1.

Domain behavior served: Preparing the two main deck piles (Encounter deck and Treasure deck) for a new game.

User-visible outcome served: Ensure card variety matches game expectations and no "unknown" cards are mixed into the match decks.

Boundaries touched by the human: SQL seed files (e.g., walkthrough/database/05_seed_deck_cards.sql or similar path), schema validation tests.

Out of scope: Actually shuffling cards or running gameplay code (dealt with in T06/T07).

Relational Deck Layout

Ensure your schema has a table structure matching these concepts:

  • decks: id (PK), name (e.g., 'Encounter Deck', 'Treasure Deck').
  • deck_cards: deck_id (FK), card_id (FK), quantity (INT > 0). PK is (deck_id, card_id).

Red Slice

  1. Write an integration SQL script (or within CTest) that runs a query checking for empty decks or invalid card mappings (e.g. cards mapped to a deck with 0 or negative quantities).
  2. Run the validation query on an unseeded database; it must return a failure or zero rows.

Green Slice

  1. Write the SQL seed data mapping v0.1 cards to decks in a new seed script (e.g., walkthrough/database/05_seed_deck_cards.sql or equivalent template).
  2. Write SQL validation queries that check that 'Encounter Deck' has at least 1 monster and 1 curse, and 'Treasure Deck' has at least 1 equipment.
  3. Verify database verification scripts run successfully during the build pipeline.

Refactor Slice

  1. Ensure 'The Singularity' card has a quantity of exactly 1 in the Encounter deck to avoid overwhelming players in early turns.
  2. Clean up queries using standard INNER JOIN commands instead of subqueries where possible.

Concrete Examples

Example Seed Script (walkthrough/database/05_seed_deck_cards.sql)

-- Seed Decks
INSERT INTO decks (id, name) VALUES
(1, 'Encounter Deck'),
(2, 'Treasure Deck')
ON CONFLICT (id) DO NOTHING;

-- Map Cards to decks
-- Assume card ids: 1: Legacy Code Monster, 2: ThinkPad, 3: Broken CI, 4: Scope Creep, 5: Emacs Mastery, 6: The Singularity
INSERT INTO deck_cards (deck_id, card_id, quantity) VALUES
(1, 1, 4), -- 4 copies of Legacy Code Monster in Encounter Deck
(1, 3, 3), -- 3 copies of Broken CI in Encounter Deck
(1, 4, 3), -- 3 copies of Scope Creep in Encounter Deck
(1, 6, 1), -- Only 1 copy of The Singularity (Boss) in Encounter Deck
(2, 2, 2), -- 2 copies of ThinkPad in Treasure Deck
(2, 5, 2)  -- 2 copies of Emacs Mastery in Treasure Deck
ON CONFLICT (deck_id, card_id) DO UPDATE SET quantity = EXCLUDED.quantity;

Example SQL Validation Query

-- Query to validate deck counts and properties.
-- Must return 0 rows to indicate NO ERRORS.
SELECT deck_id, card_id, quantity
FROM deck_cards
WHERE quantity <= 0;

-- Must verify Encounter Deck is populated
SELECT COUNT(*) FROM deck_cards WHERE deck_id = 1 HAVING COUNT(*) = 0;

Review Checks

  • Verify make db-seed executes the deck mapping seed.
  • Confirm that cards mapped to the Encounter deck are restricted to Monsters, Curses, and AI/threats, while the Treasure deck only contains Equipment.

Definition Of Done

  • Deck-card mappings exist in the database after seeding.
  • Validation constraints verify that all quantities are greater than zero.
  • No compilation or database integrity errors occur.
