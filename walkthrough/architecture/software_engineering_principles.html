Software Engineering Source of Truth

This document defines the architecture principle that all technical approaches and decisions for Dungeons and Devs must satisfy.

Principle

The domain is the source of truth. Strategic understanding comes before tactical structure.

Every technical decision must first explain which domain capability, business/gameplay rule, player outcome, or team communication problem it serves. Code structure, Clean Architecture layers, Docker, CMake, repositories, entities, value objects, SQL schemas, and protocol shapes are tools. They are justified only when they make the domain clearer, safer, more testable, or easier to evolve.

For this project, "business" means the actual product domain: the game experience, player progression, card/content rules, match lifecycle, release constraints, and the language shared by designers, engineers, database, DevOps, and product mentors.

Decision Order

  1. Understand the domain. Name the gameplay/business capability, user story, rule, invariant, or operational need.
  2. Map the boundary. Decide which context owns the language and behavior: gameplay rules, match orchestration, content loading, persistence, terminal rendering, runtime environment, or release readiness.
  3. Choose the simplest tactical shape. Apply entities, value objects, repositories, services, adapters, Docker, CI gates, or SQL structure only when they support the mapped boundary.
  4. Protect feedback loops. Make the decision testable through CTest, SQL validation, fixed-seed simulation, manual terminal playtest, or release checklist evidence.
  5. Revisit when the domain changes. Refactor structure when learning invalidates the previous model.

Decision Tests

Before accepting any technical approach, answer these questions:

  • What domain capability or product risk does this decision serve?
  • Which bounded context owns the language and behavior?
  • Can the domain expert, designer, or product owner understand the terms used in the model?
  • Is this tactical pattern required by current complexity, or is it ceremony copied from a template?
  • Does this preserve deterministic rules, server-authoritative command flow, and testable feedback?
  • Can it be verified with a concrete gate: unit test, SQL validation, fixed-seed transcript, Docker/Compose check, or manual playtest?

Anti-Patterns

Do not start with tactical DDD templates, repository boilerplate, Docker topology, database tables, or folder structures and then force the domain to fit them.

  • Adding aggregates, entities, value objects, or repositories before the language and boundaries are understood.
  • Using Clean Architecture as a folder ritual instead of a dependency and ownership discipline.
  • Letting infrastructure convenience change domain rules or test boundaries.
  • Containerizing complexity that has not yet been understood.
  • Accepting a technical decision that cannot name the gameplay, business, or learning outcome it protects.
