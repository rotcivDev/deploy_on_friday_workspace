T01 Architecture Review: Cycle Boundary And Deferred Scope

Decision

T01 is complete when v0.1 has one accepted boundary rule: implementation work is accepted only when it serves a player-visible domain behavior, deterministic feedback loop, content validation need, or local release-readiness risk.

The v0.1 cycle remains a local Root Prototype. It should prove a complete Level 1 to Level 10 match with one human player, two deterministic bots, seeded content, in-memory rules, replayable simulation, and a terminal playtest. Clean Architecture, CMake, Docker/Compose, PostgreSQL, and NCurses are tactical supports for that outcome, not independent goals.

Review Checklist

Use this checklist before accepting any task into the v0.1 implementation cycle.

  • Does the task name the gameplay behavior, content rule, deterministic check, or release risk it protects?
  • Does the task preserve the dependency direction: client to application, application to domain and ports, infrastructure behind ports?
  • Can the task be verified by CTest, SQL validation, fixed-seed transcript, Docker/Compose check, or manual terminal playtest?
  • Does the task keep pure domain/application tests independent of PostgreSQL, NCurses, sockets, pthreads, and filesystem fixtures?
  • Does the task avoid pulling deferred v0.2 concerns into v0.1?
  • Does the task keep human and bot actions routed through application commands instead of UI-owned rule mutation?
  • Does the task return structured results or events when the UI needs to explain what happened?

Deferred Scope

The following are explicitly out of the v0.1 first development cycle unless a later product decision replaces this boundary review:

  • TCP multiplayer server/client synchronization, sockets, packet routing, reconnect, spectator mode, and shared binary protocol structs.
  • pthread worker pools, connection pools, production runtime concurrency, and lobby orchestration.
  • Persistent accounts, authentication, rankings, achievements runtime, inventory persistence, and match history.
  • Required JSONB game_events writes during normal play. Runtime events stay in application/domain result flow for v0.1.
  • Cloud deployment, Kubernetes, production image publishing, production secrets platforms, and production observability stacks.
  • Full PvP card play, trading, negotiation economies, equipment slot limits, deep Influence economy, and class-specific active abilities.
  • Large card expansion, rarity balancing pass, AI chain reactions, and complex bot intelligence beyond deterministic baseline rules.

Boundary Notes

    sends intentions and renders snapshots

            coordinates commands, ports, snapshots, bot orchestration

                    owns deterministic rules, cards, decks, players, match state
            -> application ports
                <- infrastructure/postgresql

  • Domain headers must not include libpq-fe.h, ncurses.h, POSIX socket headers, pthread headers, or application service headers.
  • Application services may call domain functions and application ports, but must not issue SQL or render terminal panels.
  • Infrastructure adapters convert database rows into plain content definitions before returning data.
  • The NCurses client renders only application snapshots and uses stable IDs or indexes supplied by the application.
  • Every command result should include status, typed error where needed, updated snapshot, and ordered events.
