Technical Naming Policy

Architecture and systems guidance for decoupling product branding from implementation identifiers.

Decision

Product names must not become code prefixes. The public title is a marketing and product artifact. C symbols, CMake targets, database names, protocol constants, package namespaces, and service identifiers must use stable technical naming instead.

Deploy on Friday is the current public product title. Implementation examples must not use title-derived prefixes. Documentation examples now use game_ as the stable generic technical prefix because it describes the software system without binding it to the current public title or to one mechanic.

Why This Matters

  • Public titles are product decisions and must not force code, database, build, or protocol renames.
  • Renaming C symbols, targets, database names, and protocol fields late is expensive and risky.
  • Brand-coupled identifiers leak marketing volatility into stable architecture.
  • Generic technical names are less expressive than domain names, but they are safer than product-title initials when the title is not final.

Human Implementation Rule

  • When creating new C files, headers, CMake targets, SQL examples, Make targets, protocol names, or test binaries, prefer game_ for project-owned examples.
  • Do not introduce abbreviations derived from the current product title unless the team explicitly approves a stable technical codename.
  • Keep player-facing strings free to use the public product title; those are presentation content, not stable architecture.
  • If the public name changes, product copy should change without requiring domain/API/schema renames.

Review Checklist

  • Does this identifier still make sense if the public title changes?
  • Is this name stable enough to survive store-page, logo, and naming-risk changes?
  • Would changing this name require database migrations, protocol changes, or public API churn?
  • Does the name preserve the domain-first source-of-truth principle?
