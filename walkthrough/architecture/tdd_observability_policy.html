TDD and Observability Engineering Policy

Decision

TDD and observability are non-negotiable engineering approaches for Deploy on Friday.

No production behavior is accepted without a prior failing check and observable evidence that explains what happened, who or what initiated it, which state changed, and how the behavior can be replayed or audited.

This extends the domain-first engineering principle. The domain remains the source of truth, and every domain decision must be testable and observable from the first implementation slice.

What Observability Means

Observability is not just monitoring dashboards. Monitoring answers whether a system appears healthy. Observability lets the team explain a specific behavior after the fact from emitted evidence.

ConcernPolicy
GameplayEvery command returns structured events, typed outcomes, and enough state references to explain card effects, combat, rewards, curses, bot decisions, and match completion.
UsersOnline play must identify the account or session that issued each command, enforce quota and cooldown policy, and preserve replayable command evidence. Local play can use deterministic local actor identifiers.
OperationsBuild, test, seed, validation, simulation, and playtest flows must emit actionable diagnostics that identify the failed gate and the relevant seed, fixture, command, or component.
Product ControlThe product must support operational control over access, abuse prevention, demo quotas, abandoned-match cooldowns, match reconstruction, and incident investigation without collecting unnecessary personal data.
PrivacyAuditability does not mean indiscriminate surveillance. Store stable actor/session identifiers and operational facts needed for control, debugging, support, and abuse prevention. Avoid raw secrets, private messages, terminals dumps, or unrelated personal data.

Required Event Envelope

The exact C structs and database schema can evolve, but every command/event design must account for these fields or explicitly document why a field is not applicable for the current slice.

game_event {
  event_id
  occurred_at_or_tick
  correlation_id
  causation_id
  source_component
  actor_id_or_local_actor
  account_id_or_session_id
  match_id
  turn_id
  command_type
  command_sequence
  rng_seed
  rng_step_or_draw_index
  card_id_or_effect_id
  target_actor_id
  event_type
  result_status
  error_code
  quota_or_cooldown_decision
  public_message
  schema_version
}

For v0.1 local play, some values can be deterministic placeholders such as local-human-1, bot-legacy-maintainer, or local-session. The important rule is that the shape exists before online multiplayer depends on it.

XP Policy

Every implementation task follows this sequence:

  1. Red: write the failing unit test, integration check, SQL validation, transcript expectation, or playtest checklist first. The red check must include the expected observable signal whenever the behavior changes system state.
  2. Green: implement the smallest behavior that satisfies the rule and emits structured evidence.
  3. Refactor: improve naming, boundaries, and ownership without weakening test coverage or observability.
  4. Gate: prove the behavior through test output, event transcript, log sample, replay seed, or manual playtest note.

A story is not done if the feature works but the team cannot explain the exact command path, actor/session, seed, state transition, emitted events, and failure mode from artifacts.

Control Model

The system must give product and operations a reliable control plane from the beginning:

  • Know which local actor, bot, session, or account initiated every command.
  • Know which match, turn, command sequence, card, effect, seed, and RNG step produced every important outcome.
  • Know whether a command was accepted, rejected, rate-limited, blocked by quota, blocked by cooldown, or failed due to infrastructure.
  • Know enough to reconstruct a support case, abuse case, replay mismatch, abandoned match, or balance problem.
  • Keep this control privacy-aware: operational identifiers and product facts are required; unrelated personal data is not.

Release Gates

  • No production behavior without a failing check written first.
  • No command without a structured result and event trail.
  • No random behavior without a replay seed and reproducible transcript path.
  • No online command without actor/session identity, correlation id, and authoritative quota/cooldown decision.
  • No release candidate without archived test output, DB validation output, simulation transcript, log sample, and playtest notes.
  • No observability stack may be used as a substitute for clear domain/application events. External tools can ingest the facts; they do not define the facts.

Examples

Command Result Shape

command: RESOLVE_COMBAT
actor_id: local-human-1
match_id: local-match-777
turn_id: 12
correlation_id: cmd-000184
rng_seed: 777
events:
  - COMBAT_STARTED card=the-merge-conflict actor=local-human-1
  - POWER_COMPARED actor_power=8 monster_power=7 result=win
  - LEVEL_CHANGED actor=local-human-1 from=3 to=4
  - TREASURE_DRAWN card=linux-mastery draw_index=41
status: accepted

XP Acceptance Example

  • Red: a combat test asserts a win emits COMBAT_STARTED, POWER_COMPARED, LEVEL_CHANGED, and a replay seed.
  • Green: the domain returns those events and the application command result preserves order.
  • Refactor: event construction is centralized without adding infrastructure dependencies to the domain.
  • Gate: make test passes and make simulate GAME_MATCH_SEED=777 writes a transcript containing the same event order.
