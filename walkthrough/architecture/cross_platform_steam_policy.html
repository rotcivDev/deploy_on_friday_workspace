Cross-Platform and Steam Distribution Policy

Decision

Windows, macOS, Linux, and Steam distribution are first-class engineering concerns for Deploy on Friday.

Core gameplay can start local and terminal-driven, but each durable production feature must preserve a path to native platform builds, a better Steam-ready shipping UI, authoritative server decisions, and replaceable adapters for Steam-delegated synchronization.

This policy complements TDD and observability and technical naming. It exists to prevent late platform rewrites and to keep Steam integration outside the domain model.

Shipping UI Policy

ncurses is acceptable for v0.1 learning, debugging, and local smoke play. It must not be treated as the final Steam shipping UI unless it can satisfy the product's Windows, macOS, Linux, Steam Overlay, controller, readability, and Steam Deck goals.

The long-term client should be shaped as a replaceable rendering/input adapter around the same application commands and snapshots. A graphics-backed terminal-style shell using a portable game/window/input layer is the preferred direction for Steam because it gives the product control over font metrics, window size, controller navigation, overlay behavior, and handheld readability.

A task that adds UI behavior must not move rules into the UI. The client sends intentions and renders authoritative snapshots; the application/server path validates and mutates state.

Authoritative Server Rules For Achievements And Stats

Achievements and stats are game facts, not storefront side effects. The authoritative command path decides whether a player earned an achievement, incremented a stat, consumed a demo quota, triggered a cooldown, unlocked an extension recipe, or completed a match.

  • The client may display achievement/stat changes, but it must not be the authority that decides them.
  • Local-only play may simulate the server-authoritative path through the application layer with deterministic local actors and sessions.
  • Official online multiplayer must make achievement and stat decisions on the server side or through a server-controlled application service.
  • Steam sync adapters may publish authoritative achievements/stats to Steam, but they must not define the game rule that grants them.
  • Every achievement/stat mutation must be tied to command evidence: actor/session, match, turn or completion marker, correlation id, result, and replay seed when applicable.

Steam-Delegated Sync Uses Adapters

All synchronization that may later be delegated to Steam must be represented as ports with local stubs first. This keeps local development, automated tests, and non-Steam builds viable while preserving the Steam launch path.

Steamworks C++ integration, when introduced, belongs in infrastructure/client adapter code with a flat C boundary if needed. Domain and application interfaces should remain independent of Steam headers and AppIDs.

Release Gates

  • No durable gameplay feature is accepted if it makes Windows, macOS, Linux, or Steam distribution materially harder without documenting the tradeoff.
  • No final shipping UI commitment is accepted until it proves controller navigation, readable card text, stable layout, and a Steam-friendly window/overlay path.
  • No achievement or stat is accepted unless the authoritative command path produces the grant/increment decision before any Steam sync call.
  • No Steam feature is accepted directly in domain rules. Use ports, adapters, and local stubs first.
  • No local stub is accepted if it cannot be replaced by a Steam adapter without changing game rules.
  • No platform-specific implementation is complete without observable evidence in the test transcript, build artifact, or release checklist.

Examples

Adapter-Oriented Sync Flow

application command: COMPLETE_MATCH
authoritative result:
  actor_id: local-human-1
  match_id: local-match-42
  result: won
  achievements_granted: ["first-friday-deploy"]
  stats_incremented: { matches_completed: 1, wins: 1 }
sync ports called after authoritative result:
  game_achievement_sync_port.grant("first-friday-deploy")
  game_stats_sync_port.increment("matches_completed", 1)
local stub behavior:
  append JSONL evidence to .local/game_achievements.jsonl
future Steam adapter behavior:
  publish the same authoritative facts through Steamworks

Shipping UI Boundary

client input:
  controller A on "Resolve Combat"
client sends:
  GAME_COMMAND_RESOLVE_COMBAT(match_id, actor_id, selected_card_id)
application/server returns:
  snapshot + ordered events + achievements/stats candidates
client renders:
  card animation, log line, achievement toast
client does not:
  calculate combat, grant achievement, update stat authority, or mutate match state
