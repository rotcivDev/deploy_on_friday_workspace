Lead Architecture Backlog Refinement Guide: v0.1 Prototype

This document evaluates kickoff_backlog.html together with the database, gameplay, and systems refinement guides. It consolidates the team plans into one architecture-led increment sequence for the v0.1 Root Prototype.

This is a mentorship and support artifact. It does not require agents to edit production source directories.

  • db_refinement_guide.html: content loading, deck membership, application repository port, and deferred JSONB event persistence.

2. Architecture Review Summary

Second Review: Source-of-Truth Alignment. Architecture must treat strategic domain understanding as the source of truth. Clean Architecture remains the right operational boundary discipline, but it is not the starting point. The team should first name the gameplay/business capability and bounded context, then use layers, ports, adapters, and build targets only to protect that domain model. Tactical DDD patterns are optional and should be introduced only when current domain complexity justifies them.

The backlog is now directionally coherent: all team roles are aiming at a local, deterministic, three-player prototype where PostgreSQL provides seeded content, the game loop runs in memory, and the terminal client renders application snapshots.

The main architecture risk is sequence drift. If implementation starts from the UI or database adapter too early, the project can accidentally bypass the clean command boundary and push rule decisions into the wrong layer.

Architecture recommendation:

  • Start by enforcing build targets and dependency rules.
  • Define domain/application data contracts before writing adapters or UI behavior.
  • Load and validate content once at match startup.
  • Keep match state and random state in memory for v0.1.
  • Keep event persistence, sockets, pthreads, protocol structs, accounts, rankings, and achievements deferred.

3. Target v0.1 Dependency Shape


flowchart LR
    UI[client/ncurses\nrenders snapshots\nsends commands]
    APP[application\nmatch service\ncommands/results\nports]
    DOM[domain\ncards decks players\nrules RNG-owned inputs]
    PORT[application ports\ncontent_repository]
    DB[infrastructure/db\nPostgreSQL adapter]
    TESTS[tests\nfakes and simulations]

    UI --> APP
    APP --> DOM
    APP --> PORT
    DB --> PORT
    DB --> APP
    TESTS --> APP
    TESTS --> DOM

Boundary notes:

  • domain/ must not include PostgreSQL, NCurses, sockets, pthreads, filesystem, or application service headers.
  • application/ owns orchestration, commands, ports, snapshots, bot turn flow, and startup validation.
  • infrastructure/db/ owns libpq, SQL, row mapping, and database connection lifecycle.
  • client/ owns NCurses rendering and input translation only.
  • shared/ stays deferred for v0.1 unless a type is genuinely needed by multiple runtime binaries. For the local prototype, application command structs are enough.

4. Team Finding Synthesis

Finding 1: The Build Boundary Must Come First

Systems identified that a single all-in-one executable would hide architecture violations. A1 must be the first implementation gate.

Decision:

  • Create layered targets before real gameplay code expands.
  • Let target dependencies prove that domain/application do not need libpq or NCurses.
  • Keep DB adapter tests separate from normal domain/application tests.

Finding 2: Content Loading Is An Application Port, Not A Domain Concern

Database refinement correctly moved repository guidance from a domain repository to an application content port.

Decision:

  • The application starts a match by calling a content repository port.
  • Infrastructure returns plain content definitions.
  • Domain receives values, not database handles or SQL IDs as rule drivers.
  • Missing content returns a startup failure rather than constructing an empty match.

Finding 3: Gameplay Balance Needs Fixture Support

Game design identified that the current card set has weak early progression coverage. Architecture should support scripted fixtures without hardcoding game logic into the UI or DB adapter.

Decision:

  • Content validation should know required card/deck presence.
  • Deterministic deck tests should accept fixed seed and, when needed, fixture draw order.
  • The domain should support card properties and rule keys without embedding database queries.

Finding 4: Determinism Is A Cross-Cutting Contract

Systems and gameplay both depend on reproducible shuffles and bot behavior. This cannot be hidden in utility globals.

Decision:

  • Store seed and RNG state in match/application state.
  • Pass RNG state explicitly into deck shuffle and bot decisions.
  • Do not call rand() from domain rules.
  • Record seed in events/logs for replay.

Finding 5: Events Are Runtime Results Before They Are Database Rows

The database guide defers JSONB event persistence, while systems and kickoff backlog require structured event results for UI logs.

Decision:

  • v0.1 event structs live in domain/application result flow.
  • UI formats events into text but does not infer rules from state.
  • game_events persistence remains optional and deferred until after the local loop works.

  • Build target plan review.

AR1. Layered Build And Test Boundary

Outcome: make forbidden dependencies fail early.

Consumes:

  • Systems SP0.
  • Kickoff A1.

Scope:

  • Establish domain, application, infrastructure DB, client, and test targets.
  • Keep libpq in infrastructure DB only.
  • Keep NCurses in client only.
  • Keep pure domain/application tests runnable without PostgreSQL or NCurses.

Acceptance criteria:

  • Domain builds against the C standard library only.
  • Application builds against domain and application ports only.
  • Infrastructure DB is the only PostgreSQL-linked target.
  • Client is the only NCurses-linked target.

Verification:

  • make build
  • make test
  • Include/dependency smoke review.

AR2. Content Contract And Startup Gate

Outcome: make R1 safe by preventing empty or partial content from creating a match.

Consumes:

  • Database DB0, DB2, DB3.
  • Gameplay GD0.
  • Kickoff R1, A3.

Scope:

  • Define application content repository contract.
  • Define required v0.1 content groups: card types, classes, encounter cards, treasure cards, deck membership.
  • Return typed startup failures for missing content.
  • Keep PGconn, PGresult, SQL, and connection lifecycle private to infrastructure.

Acceptance criteria:

  • Application receives plain content definitions.
  • Missing required content produces readable startup failure.
  • Domain receives card/class values only.

Verification:

  • Fake repository startup tests.
  • Optional local PostgreSQL adapter mapping tests.

AR3. Domain Model, Decks, And Deterministic RNG

Outcome: make R2, R3, and A6 testable without UI or DB runtime dependencies.

Consumes:

  • Systems SP1, SP2.
  • Gameplay GD1.
  • Database DB1.
  • Kickoff R2, R3, A2, A6.

Scope:

  • Model cards, decks, discard piles, players, equipment, and match state as pure domain/application values.
  • Define seedable RNG state.
  • Build deterministic Encounter and Treasure decks from loaded content.
  • Keep shuffle and discard behavior reproducible.

Acceptance criteria:

  • Same seed creates the same draw order.
  • Decks can reshuffle discard piles deterministically.
  • Domain tests do not require PostgreSQL or NCurses.

Verification:

  • Fixed-seed deck tests.
  • Domain lifecycle tests.

AR4. Rule Results, Combat, Curses, And Events

Outcome: make R4, R5, and A7 produce structured results the application and UI can trust.

Consumes:

  • Systems SP2, SP3.
  • Gameplay GD2, GD3.
  • Kickoff R4, R5, A7, A8.

Scope:

  • Define combat resolver input/output shape.
  • Define curse state transitions and expiry.
  • Emit structured events for draw, curse, combat, reward, equipment, bot action, and match end.
  • Define ownership for result arrays and snapshots.

Acceptance criteria:

  • Win/loss/Level 10 outcomes are deterministic.
  • Invalid commands do not mutate state.
  • Event order is testable.
  • Public interfaces have ownership comments.

Verification:

  • Domain rule tests.
  • Application command tests.
  • Optional leak-check run.

AR5. Application Command Boundary And Bot Orchestration

Outcome: ensure human and bot actions use the same authoritative path.

Consumes:

  • Systems SP3.
  • Gameplay GD4.
  • Kickoff R6, A4.

Scope:

  • Define command names for start match, kick backlog, equip, play, request help, resolve combat, resolve bot turn, and end turn.
  • Route bot decisions through application commands.
  • Keep bot logic deterministic and seed-driven.
  • Return snapshots and events from every command.

Acceptance criteria:

  • Human and bot actions share validation.
  • Bot choices replay with the same seed.
  • Invalid phase errors leave state unchanged.

Verification:

  • Application command tests.
  • Fixed-seed full-match simulation.

AR6. Snapshot-Based NCurses Boundary

Outcome: keep the UI replaceable and unable to own game rules.

Consumes:

  • Systems SP5.
  • Gameplay GD5.
  • Kickoff R7, A5.

Scope:

  • Define snapshot fields: active player, phase, player summaries, visible encounter, hand view, equipment view, actions, and recent events.
  • UI renders snapshots and sends commands.
  • UI does not recalculate Power, rewards, legality, or combat outcomes.
  • Provide static snapshot smoke path and manual resize checklist.

Acceptance criteria:

  • UI can render a static snapshot.
  • UI command selection uses stable IDs or indexes supplied by application.
  • Terminal redraw does not mutate domain state.

Verification:

  • Static layout smoke test if feasible.
  • Manual terminal playtest checklist.

AR7. Playable v0.1 Vertical Slice

Outcome: integrate R1-R7 into one local match loop.

Consumes:

  • AR1-AR6.
  • Gameplay GD5.
  • Systems test matrix.

Scope:

  • Start match from validated content.
  • Build deterministic decks.
  • Run human and bot turns through commands.
  • Resolve combat, curses, equipment, help, and sabotage.
  • Render logs and snapshots.
  • End immediately at Level 10.

Acceptance criteria:

  • One human and two bots can complete a local match.
  • A fixed seed replays the same major event sequence.
  • The UI never directly mutates match state.
  • No v0.1 code requires sockets, pthread worker pools, shared protocol structs, accounts, rankings, achievements, or match history.

Verification:

  • Fixed-seed full-match simulation.
  • Manual NCurses playtest.
  • Architecture boundary review.

Content Load Flow


application_start_local_match(seed, content_repository)
    -> content_repository.validate_required_v0_1_content()

Domain Rule Boundary


combat_result = resolve_combat(combat_input)
curse_result = resolve_curse(curse_input)
power = calculate_power(player_view, temporary_modifiers)

The domain should not know whether the input came from PostgreSQL, a fake repository, a scripted fixture, or a future network message.

8. Architecture Checklist

Use this checklist at the end of each increment:


Does domain compile without libpq, ncurses, sockets, pthreads, or application services?
Does application avoid SQL, terminal rendering, and socket calls?
Do infrastructure adapters keep external library types private?
Does client render snapshots and send commands only?
Can tests run domain/application behavior without PostgreSQL?
Does every mutable command return explicit status, events, and snapshot data?
Is RNG state explicit and replayable?
Are ownership rules documented for allocated results and borrowed views?
Are v0.2 concerns still deferred unless explicitly chosen as a spike?

If any answer is no, stop and refine the boundary before adding more gameplay behavior.
