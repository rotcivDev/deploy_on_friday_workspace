Database Backlog Refinement Guide: v0.1 Prototype

This document evaluates the database impact of walkthrough/architecture/kickoff_backlog.html and refines the database work into increments for the v0.1 Root Prototype.

This is a mentorship and support artifact. It does not require agents to edit production source directories.

1. Backlog Review Summary

Second Review: Source-of-Truth Alignment. The database model must follow the domain language: card definitions, classes, deck membership, content validation, and later match events. PostgreSQL tables and repository ports are tactical choices that serve content loading and validation. Avoid designing persistence around generic DDD templates, account tables, rankings, or event sourcing until the v0.1 gameplay and match lifecycle require them.

The kickoff backlog is directionally sound for a local, playable v0.1 prototype: seeded PostgreSQL content feeds an in-memory match, while the domain and application layers keep deterministic game behavior outside the database.

The database plan needs three refinements before implementation starts:

  • Keep v0.1 database access focused on content loading: card types, classes, card definitions, decks, and deck membership.
  • Move repository guidance to the application boundary. The kickoff backlog correctly refines the older domain/repositories/card_repository.h idea into an application port such as application/ports/content_repository.h.
  • Add explicit deck composition data. The current schema has decks and deck_cards, but the seed files create deck names without linking cards into Encounter and Treasure draw piles.

Persistent accounts, rankings, achievements, inventory, and match history already exist in the schema as future-facing tables, but the kickoff backlog defers them from the first playable refinement. Do not let those tables expand v0.1 scope.

2. v0.1 Database Scope

In Scope

  • Validate seeded card_types include MONSTER, TREASURE, CURSE, EVENT, EQUIPMENT, PVP, and AI.
  • Validate seeded classes include the six starting classes listed in R1.
  • Load card definitions needed by R1, R2, R3, R4, and R5.
  • Load deck definitions and deck_cards.quantity values for deterministic Encounter and Treasure deck construction.
  • Provide clear startup failures when required content is missing.
  • Provide SQL validation queries and fixture expectations for repository/content tests.

Out Of Scope For v0.1

  • Persisting full match history.
  • Writing game_events during normal play.
  • Account authentication, password handling, rankings, achievements, and player inventory updates.
  • Connection pooling, migrations automation, or deployment automation.
  • Querying PostgreSQL during each turn. The match should load content at startup and then run in memory.

3. Backlog Alignment Findings

Finding 1: R1 Needs A Seed Validation Contract

R1 asks for a seeded content smoke test. The database plan should make this a first-class startup gate, not a loose manual check.

Recommended validation:


SELECT name
FROM card_types
ORDER BY name;

SELECT name
FROM classes
ORDER BY name;

SELECT ct.name AS card_type, COUNT(*) AS card_count
FROM card_definitions cd
JOIN card_types ct ON ct.id = cd.card_type_id
GROUP BY ct.name
ORDER BY ct.name;

Acceptance target:

  • All seven card types exist.
  • All six starting classes exist.
  • At least one MONSTER, AI, CURSE, and EQUIPMENT card exists.
  • Startup fails with a readable missing-content message if any required group is empty.

Finding 2: R2 And R3 Need Deck Membership Seeds

The schema supports deck composition through deck_cards, but 02_seed_core_data.sql currently creates only deck records. 03_seed_cards.sql creates card definitions, but does not assign cards to decks.

Recommended v0.1 deck mapping:

  • Core Monster Deck: MONSTER, AI, and CURSE cards used as the Encounter deck.
  • Treasure Deck: EQUIPMENT cards used as rewards.
  • Curse Deck: optional in v0.1 unless a separate curse-only test deck is useful.
  • AI Chaos Deck: optional in v0.1 unless AI cards need a separate expansion fixture.

Recommended validation:


SELECT d.name AS deck_name, ct.name AS card_type, cd.name AS card_name, dc.quantity
FROM deck_cards dc
JOIN decks d ON d.id = dc.deck_id
JOIN card_definitions cd ON cd.id = dc.card_definition_id
JOIN card_types ct ON ct.id = cd.card_type_id
ORDER BY d.name, ct.name, cd.name;

Acceptance target:

  • Encounter deck has all R2 candidate threats and curses.
  • Treasure deck has the initial R3 equipment target: ThinkPad, Linux Mastery, PostgreSQL Expertise, and Emacs Mastery.
  • Every deck_cards.quantity is positive.

Finding 3: Repository Shape Should Match A3

The database adapter should implement an application port, not a domain repository and not a domain-visible database connection.

Recommended shape:


application/ports/content_repository.h
    declares content loading operations and plain result structs

infrastructure/db/postgresql_content_repository.c
    owns libpq connection lifecycle, SQL, and row mapping

domain/
    receives card/class definitions as plain values only

The application port should return content definitions and typed errors. It should not return PGconn, PGresult, SQL strings, or infrastructure-owned row buffers.

Finding 4: JSONB Event Persistence Should Stay Deferred

A7 correctly says event payloads can be simple structs in v0.1 and JSONB persistence can be added later. The existing game_events table and GIN index are useful for v0.2+ but should not become part of the first playable slice unless the user explicitly chooses an event-persistence spike.

Recommended v0.1 posture:

  • Keep game_events schema documented and available.
  • Do not require runtime writes to game_events.
  • Use the application/domain event structs for logs and deterministic replay tests.
  • Add JSONB persistence only after the local turn loop is playable.

4. Increment Plan

DB0. Schema And Seed Baseline Review

Outcome: confirm the walkthrough SQL files can initialize a local database without relying on production code.

Scope:

  • Apply 01_schema.sql, 02_seed_core_data.sql, 03_seed_cards.sql, and 04_seed_achievements.sql.
  • Run the R1 validation queries.
  • Record missing content or schema mismatches in this guide or a follow-up support note.

Acceptance criteria:

  • Schema loads cleanly.
  • Core card types and classes are present.
  • Card definition counts match the R1 expectations.

Verification:

  • Manual psql run or local database smoke test.

DB1. Deck Composition Seed Template

Outcome: make R2 and R3 possible by defining deck membership and quantities.

Scope:

  • Add a support SQL template, suggested as walkthrough/database/05_seed_deck_cards.sql, or extend the existing seed guide with deck membership inserts.
  • Link Encounter deck cards to Core Monster Deck.
  • Link equipment cards to Treasure Deck.
  • Keep quantities explicit so deterministic tests can assert deck size.

Acceptance criteria:

  • Core Monster Deck contains the R2 candidate threats and curses.
  • Treasure Deck contains the R3 equipment cards.
  • No deck_cards row has quantity <= 0.
  • Running the seed twice should not create duplicate membership rows. Use ON CONFLICT where appropriate.

Verification:

  • Query deck_cards by deck and card type.
  • Assert expected deck sizes before in-memory shuffling starts.

DB2. Content Repository Contract

Outcome: define the data returned by the database adapter before production implementation.

Scope:

  • Document an application port for content loading.
  • Include operations for loading classes, all cards, and cards by deck.
  • Define ownership expectations for returned arrays.
  • Define typed failures for missing content, database unavailable, and row mapping errors.

Acceptance criteria:

  • Application receives plain card/class/deck definition structs.
  • Infrastructure keeps libpq types private.
  • Repository startup failure prevents an empty match from starting.

Verification:

  • Fake repository test for application match setup.
  • Database adapter mapping test against the walkthrough seed data.

DB3. Startup Content Gate

Outcome: fail fast when local content is incomplete.

Scope:

  • Validate required card types, classes, deck names, deck membership, and minimum counts before match creation.
  • Treat AI cards as encounter threats for v0.1 unless a later rule resolver separates them.
  • Return readable diagnostic messages such as missing deck card: Treasure Deck -> ThinkPad.

Acceptance criteria:

  • Empty or partially seeded databases do not start a match.
  • Valid walkthrough seed data passes.
  • Validation does not require persistent player accounts or match history.

Verification:

  • Content smoke test with valid seed data.
  • Negative tests with missing card type, missing class, missing deck card, and zero quantity.

DB4. Optional Event Persistence Spike

Outcome: prepare for v0.2 persistence without blocking v0.1.

Scope:

  • Document mapping from application event structs to game_events.payload.
  • Keep writes optional behind an infrastructure adapter.
  • Use match_id and JSONB payload indexes already present in 01_schema.sql.

Acceptance criteria:

  • Event persistence can be disabled for local v0.1 tests.
  • If enabled, event writes are append-only and do not affect game rule outcomes.

Verification:

  • Insert/replay smoke test only if the user chooses this spike.

5. Suggested Support SQL Template For DB1

The user can turn this into walkthrough/database/05_seed_deck_cards.sql when ready.


BEGIN;

INSERT INTO deck_cards (deck_id, card_definition_id, quantity)
SELECT d.id, cd.id, 2
FROM decks d
JOIN card_definitions cd ON cd.name IN (
    'Null Pointer Exception',
    'Legacy Monolith',
    'Production Outage',
    'Hallucinated Function',
    'Infinite Agent Loop',
    'Autonomous Junior Developer',
    'Broken CI',
    'Scope Creep',
    'Context Window Exceeded'
)
WHERE d.name = 'Core Monster Deck'
ON CONFLICT (deck_id, card_definition_id)
DO UPDATE SET quantity = EXCLUDED.quantity;

INSERT INTO deck_cards (deck_id, card_definition_id, quantity)
SELECT d.id, cd.id, 1
FROM decks d
JOIN card_definitions cd ON cd.name = 'The Singularity'
WHERE d.name = 'Core Monster Deck'
ON CONFLICT (deck_id, card_definition_id)
DO UPDATE SET quantity = EXCLUDED.quantity;

INSERT INTO deck_cards (deck_id, card_definition_id, quantity)
SELECT d.id, cd.id, 2
FROM decks d
JOIN card_definitions cd ON cd.name IN (
    'ThinkPad',
    'Linux Mastery',
    'PostgreSQL Expertise',
    'Emacs Mastery'
)
WHERE d.name = 'Treasure Deck'
ON CONFLICT (deck_id, card_definition_id)
DO UPDATE SET quantity = EXCLUDED.quantity;

COMMIT;

This keeps The Singularity rare while making the rest of the Encounter deck repeatable enough for deterministic tests.

6. Repository Port Guidance

Use this as a design target for the user-created application port. The exact C names can change to match local conventions.


typedef struct {
    int id;
    char name[50];
} content_card_type_t;

typedef struct {
    int id;
    char name[100];
    char description[512];
    int base_power_bonus;
} content_class_t;

typedef struct {
    int id;
    int card_type_id;
    char card_type_name[50];
    char name[150];
    char description[512];
    int power_bonus;
    int monster_power;
    int reward_levels;
    int reward_treasures;
    char rarity[20];
    char expansion[100];
    int deck_quantity;
} content_card_definition_t;

typedef enum {
    CONTENT_OK = 0,
    CONTENT_ERR_DB_UNAVAILABLE,
    CONTENT_ERR_QUERY_FAILED,
    CONTENT_ERR_MISSING_REQUIRED_CONTENT,
    CONTENT_ERR_OUT_OF_MEMORY
} content_result_code_t;

Recommended operations:


load_classes()
load_all_card_definitions()
load_deck_cards(deck_name)
validate_required_v0_1_content()
free_content_result()

Ownership rule:

  • Infrastructure allocates result arrays.
  • Application frees result arrays through a matching repository free function.
  • Domain never owns or sees database handles.

7. JSONB Event Guidance For Later Increments

The existing game_events table is a good future fit for replay and analytics:


CREATE INDEX idx_events_match
ON game_events(match_id);

CREATE INDEX idx_events_payload
ON game_events
USING GIN(payload);

Use JSONB when v0.2+ needs persisted logs like:


{
  "turn": 4,
  "actor": "Prompt Intern",
  "card": "Broken CI",
  "effect": "skip_next_combat"
}

For v0.1, keep event payloads in memory and let the terminal log render application/domain events from the command result.

After DB1 exists, apply the deck membership seed:


psql -v ON_ERROR_STOP=1 -d dungeons_devs -f walkthrough/database/05_seed_deck_cards.sql

Then run the validation queries from section 3. The expected result is a complete content catalog and non-empty Encounter and Treasure deck membership before the application builds any in-memory deck.
